Not scoped yet — now that the whole redesign (Steps 1-5) is done, this can get a proper visual-design pass (size, contrast, position, animation) against the finished thing rather than a moving target — see the note under [Editing UX redesign](#editing-ux-redesign-ready-to-pick-up-later).

## Automated testing scope

Scoped 2026-08-24. All three tiers done 2026-08-25.

**Tooling:** Vitest (Vite-native, shares existing config, fast) + React Testing Library + jsdom for anything that renders. For Firestore-dependent code, **mock the SDK** (`onSnapshot`, `setDoc`) rather than run the Firebase Local Emulator Suite — the emulator is more realistic but needs a Java runtime and real setup overhead; mocking is enough to test our own logic.

**Tier 1 — pure functions, no mocking (done 2026-08-25, extended 2026-08-28, 25 tests):**
- `lib/date.ts` — `dateKeyFor`, `todayKey`, `todayDayIndex`, `currentWeekDateKeys`, `formatDateShort`. Covers the UTC-midnight-parsing pitfall and week/month-boundary math directly.
- `types.ts` — `isItemDone`, `isItemScheduledOn`, `isOneTimeInPast`. The core scheduling-match logic, including one-time-date-overrides-days precedence and the past-one-time-item edit-list filter.
- `lib/storage.ts` — `normalize` (migration) and `resetCompletion`, tested against old/malformed data shapes so migrations keep working as the schema grows. `firebase/firestore` and `./firebase` are mocked in this test file so importing `storage.ts` doesn't trigger a real Firestore client in jsdom.
- Runs via `npm run test` (or `npm run test:watch`), and in CI on every PR via `.github/workflows/test.yml`.

**Tier 2 — the `useSchedule` hook, Firestore mocked (done 2026-08-25, extended through the whole editing UX redesign and sub-step reordering, 21 tests):**
- Regression test for the cursor-jump bug: asserts `mutate()`/`mutateDebounced()` update local state synchronously, in the same tick as the call, not only after the mocked async transaction resolves.
- Regression test for the overnight-reset bug: fakes only `Date` (real timers otherwise), fires a `focus` event a day later, confirms the transaction resets a stale `lastResetDate` and completion state.
- Sanity coverage for `toggleItem` (including the all-sub-steps-together case), `addItem`/`deleteItem`, and same-device write ordering for immediate (non-debounced) writes.
- `saveStatus` transitions (saving → saved → fades to idle) and the error → `retrySave` flow, without double-applying a non-idempotent mutation on retry.
- Debouncing for `setChildName`, `updateCategoryName`, `updateItemTitle`, and per-sub-step text: only the final value is ever sent per pause, `saveStatus` reflects "saving" from the first keystroke (not just once the network call starts), unrelated keys (different categories, different item fields, different sub-steps) debounce independently without interfering, an immediate write isn't blocked by a concurrent pending debounce, and a pending debounced write flushes on unmount instead of being dropped.
- `reorderSubStep` swaps with a neighbor and no-ops at either end; `restoreCategory`/`restoreItem` re-insert a deleted snapshot at its original index, fully intact, including the silent-no-op case where the parent category was also deleted in the meantime.
- Regression test for the real-device "typing sync" bug found after Step 4 UAT: an incoming snapshot must not overwrite a field still mid-debounce.
- `firebase/firestore`'s `onSnapshot`/`runTransaction`/`doc` are mocked with a small in-memory "server document," rather than the Firebase Local Emulator Suite.

**Tier 3 — component behavior (done 2026-08-25, updated through 2026-08-28, 13 tests) + a new App-level tier (added 2026-08-28, 4 tests):**
- `CategorySection` — auto-collapses once every item is done, stays open while work remains, lets the user manually reopen a collapsed section, and resets that override (re-collapsing fresh) the next time new work is completed. Never auto-collapses in edit mode. Also hides an expired one-time item from the edit-mode list while still showing recurring/future/today items.
- `ItemCard` — rewritten for Step 4 (the Done button it originally drove is gone): the recurring/one-time toggle calls `updateItemMeta` immediately on click (no Done needed) and renders the date-vs-day-picker UI correctly from `item` props. Also covers the sub-step reorder buttons (calls `reorderSubStep` with the right direction, disabled at each end).
- Presentational-only components (`ProgressBar`, `DayPicker` rendering) skipped as planned.
- RTL doesn't auto-cleanup between tests without `test.globals: true`; `src/test/setup.ts` registers `afterEach(cleanup)` explicitly so component tests don't leak DOM nodes across cases in the same file.
- **New `App.test.tsx`** (first test file for `App.tsx`, added for Step 5): the full delete → Undo-toast → restore flow end-to-end for both categories and items, auto-dismiss after the timeout, and a second delete replacing the pending toast rather than stacking. Uses the same Firestore-mocking approach as `useSchedule.test.ts`.

**Explicitly out of scope for now:** Firestore emulator / security-rule testing (rules are trivial today), end-to-end browser tests via Playwright (defer unless a class of bug keeps slipping past unit tests), visual regression testing (overkill at this scale).

**CI:** done — `.github/workflows/test.yml` runs `npm run typecheck` (new, added 2026-09-03) then `npm run test` on every pull request, pairing with the branch protection already in place so a broken test *or* a real type error blocks a bad PR before merge. **Gap found and fixed 2026-09-03:** CI previously never typechecked at all — only ran the test suite — and separately, the local verification habit of `npx tsc --noEmit` used all project long had *also* been silently checking nothing, since the root `tsconfig.json` only declares project references (`files: []`), which plain `tsc` ignores outside `--build` mode. A real type error could merge through any PR undetected and only surface at deploy time when `deploy.yml` ran the full build. New `npm run typecheck` script (`tsc -b`, the same command `npm run build` already used) is now both the correct local verification command and a required CI step. Verified the new gate actually works by deliberately introducing a type error, confirming `npm run typecheck` failed, then reverting it.

## Editing UX redesign (ready to pick up later)

Scoped 2026-08-25. **All 5 steps done as of 2026-08-28 — this redesign is fully shipped.** See [Incremental delivery plan](#editing-ux-redesign-ready-to-pick-up-later) below for the full history. The old draft/Done-button mechanism (PRs #15–16) is gone as of Step 4; it worked and was fixed, but its layered state (global Edit mode → per-item expand → per-item local draft → explicit commit) is what caused essentially every editing bug this session: the cursor-jump race, the overnight-reset data-loss bug's cousin, the unmount-during-commit bug, and the flash-revert bug. Rather than keep hardening that design, it's been replaced with a structurally simpler one.

**Core idea:** autosave with a debounce, plus a visible sync-status indicator, instead of buffering a whole item's edits until an explicit "Done" commit. This is the same pattern Notion, Linear, and Google Docs use — edit, pause, it saves, no separate mode to remember to exit.

**What changes:**
- **Remove the `ItemCard`-level draft entirely** (`Draft`/`dirty`/`commitDraft`/`finishEditing`/`draftRef`, and the per-item "Done" button). Text fields (title, notes, sub-step text, child's name) go back to calling `updateItemMeta` / `updateSubStepText` / `setChildName` directly on every `onChange`, same shape as before PR #13's per-keystroke-write days. **Done (2026-08-26) — see Step 4 below.**
- **Move debouncing into the data layer, not the component.** In `useSchedule.ts`, wrap the text-field mutation path so the *local* optimistic state still updates synchronously on every keystroke (this is what the cursor-jump fix in PR #5 depends on — must not regress it), but the actual Firestore transaction for that field is delayed ~500–600ms after the last keystroke, resetting the timer on each new one. Non-text actions (toggling done, adding/deleting an item or category, the day picker, the one-time/recurring switch) stay immediate — they're already discrete, cheap, one-shot writes with no typing race to debounce. **Done (2026-08-26) — see Steps 2-4 below.**
- **Add a `saveStatus` value exposed from the hook** (`idle` / `saving` / `saved` / `error`), derived from whether any debounce timer or in-flight transaction is currently pending, plus whether the most recent write settled or rejected. **Done (2026-08-26) — see Step 1 below.**
- **Add a small status indicator in the header** (near the Edit button or progress card): a subtle "Saving…" while pending, "Saved" that fades after a couple seconds once settled, "Couldn't save — tap to retry" if a write's promise rejects. This is the actual trust-builder — a parent should never have to wonder whether an edit stuck. **Done (2026-08-26) — see Step 1 below.**
- **Undo for destructive actions, not every edit.** Add a brief "Category deleted — Undo" / "Item deleted — Undo" toast for delete actions specifically (the one place an accidental tap is genuinely hard to recover from); routine text edits don't need it since nothing is hidden or buffered anymore — what's on screen is what's saved (or about to be), so fixing a typo is just retyping it. **Done (2026-08-28) — see Step 5 below.**
- **Keep as-is:** the Firestore transaction mechanism itself (correct, not the source of these bugs), real-time sync, the PIN-gated parental lock concept (still needed — reframe as "unlocked for editing" rather than a heavyweight "mode" if it helps, but the underlying gate stays), expand/collapse for progressive disclosure (notes/day-picker/sub-steps), and everything unrelated to saving (scheduling logic, auto-collapse, layout).
- **User feedback (2026-08-25):** the per-item "Done" button currently shows unconditionally whenever an item is expanded in edit mode, even if nothing was actually changed — maybe it shouldn't show for items that weren't edited. **Resolved (2026-08-26):** the Done button is gone entirely as of Step 4 — autosave has nothing to explicitly "finish."
- **User feedback (2026-08-26):** after using Steps 2-3, the save-status indicator (Saving…/Saved) isn't very visible — noted specifically while editing a category name. Worth a visual-design pass (size, contrast, position, maybe a brief animation) once the mechanical steps (4-5 below) are done, rather than tuning a moving target mid-redesign. Not scoped yet.

**Explicitly out of scope:** redesigning the visual layout or information architecture of the checklist itself — this is scoped purely to the save mechanism and edit affordances.

**Incremental delivery plan (added 2026-08-26):** rather than one large PR, this is being built as a sequence of small, independently-verifiable steps — each its own branch/PR, each tested live in the browser (throwaway Firestore doc, per the project's standard method) before moving to the next:

1. **Save-status indicator, wired to the *existing* write queue — no debounce/draft changes yet.** `saveStatus` is computed purely from the current `mutate()`/transaction lifecycle (`queueTransaction` in `useSchedule.ts`), so this ships the actual trust-builder UI in complete isolation from the riskier parts of the redesign. **Done 2026-08-26** — verified live: "Saving…" appears the instant a toggle fires, "Saved" shows once the transaction settles, fades to idle after ~2s. A `retrySave()` that re-queues the exact failed transaction (without re-applying the optimistic local update, so a toggle can't get double-applied) is unit-tested but couldn't be verified live — no network-throttling control available in this session's browser tooling to force a real Firestore failure.
   - **Real-device UAT (2026-08-26) surfaced two bugs, both fixed same day:** (a) the header's name/date column had no `min-w-0`/`flex-1`, and the name-edit `<input>` had no width constraint, so their intrinsic content width refused to shrink — combined with the new indicator column, this pushed "Done editing" off the right edge of narrow (mobile) screens, forcing a horizontal scroll. (b) `SaveStatusIndicator` mounted/unmounted its text entirely, so the header's height changed every time status flipped, visibly shifting the Edit button (and everything below it) — reported as the indicator feeling "very prominent." Fixed by reserving a fixed-height slot for the indicator (`min-h-4`, always rendered) so the routine saving/saved cycle never changes header height, while the rare error message is still allowed to wrap onto a second line.
   - **Real-device UAT also surfaced an unresolved gap:** testing in airplane mode produced no error state at all — "Saving…" (or nothing) with no eventual "Couldn't save." Root cause is architectural, not a Step 1 bug: `runTransaction()` requires a live connection to coordinate with the backend, so unlike plain writes (which the app's offline persistence cache can queue and sync later), a transaction has no offline path — it doesn't reject, it just stays pending until connectivity returns. The optimistic local update still flips the checkbox immediately, so nothing *looks* wrong, but the write can sit unconfirmed indefinitely with no signal to the user. This wasn't part of Step 1's scope (which only wires status to the transaction's existing resolve/reject) and needs its own decision: e.g. an `navigator.onLine`-based "Offline — will sync when reconnected" state, layered on top of `saveStatus` rather than folded into it. Not yet scoped or built — see Open decisions.
2. **Prove the debounce pattern on the child's-name field** (`App.tsx`, currently commits on blur) — switch it to per-keystroke calls through a new debounced path in the hook. Small blast radius, easy to validate (type fast, confirm no cursor jump, confirm the write lands after a pause). **Done (2026-08-26)** — added `mutateDebounced(key, fn)` in `useSchedule.ts`: same synchronous optimistic-local-update contract as `mutate()`, but the transaction is delayed `DEBOUNCE_MS` (600ms) after the last call for that key, with each new call for the same key replacing whatever was still pending (only the final value is ever sent). The pending unit of work is counted from the *first* keystroke of a debounce window (not when the timer fires), so `saveStatus` says "saving" through the whole countdown, not just once the network request starts. A pending debounced write is flushed immediately on unmount rather than dropped. Removed the old `nameDraft`/`nameSynced` local-state mirror in `App.tsx` entirely — the input now binds directly to `data.childName` / `s.setChildName`, no `onBlur` needed. Verified live: typed "S", "a", "m" ~200ms apart, indicator stayed "Saving…" through all three keystrokes and the debounce window, flipped to "Saved" once (not three times) after the pause, confirmed the value persisted after a hard reload. Unit tests cover single-write debouncing, an immediate write not being blocked by a concurrent pending debounce, and the unmount-flush. (Caught and fixed a real test-infra bug along the way: `vi.useFakeTimers({ toFake: ['setTimeout'] })` without also faking `clearTimeout` makes `clearTimeout` a no-op against fake timer IDs — silently defeated the debounce's own cancellation in tests. Fixed across all fake-timer tests in `useSchedule.test.ts`.)
3. **Extend debounce to category names** — same pattern, still outside `ItemCard`. **Done (2026-08-26), emoji excluded by choice:** added `updateCategoryName(categoryId, name)` in `useSchedule.ts`, keyed per category (`category:<id>:name`) so editing two categories' names around the same time debounces each independently — verified with a dedicated test. Category emoji intentionally stays on the old immediate `updateCategoryMeta` path (a single quick tap/paste, not sustained typing — no real debounce benefit there). Verified live: same "Saving… through the whole typing + pause window, one Saved" behavior as the name field; confirmed persistence after a hard reload.
4. **The big one: apply debounced autosave to `ItemCard`'s text fields and delete the draft machinery** (including the per-item Done button). **Done (2026-08-26).** `ItemCard` is now a plain prop-driven view with no local edit state beyond `expanded`/`newSubStep` — title/notes/sub-step text bind directly to `item.*` and call new debounced hook setters (`updateItemTitle`, `updateItemNotes`, `updateSubStepText`, each keyed per item+field via a new `updateItemDebounced` helper, so editing two fields — or two sub-steps — on the same item debounces independently). Emoji, the day picker, and the one-time/recurring toggle stay on the immediate `updateItemMeta` path (narrowed to just `emoji`/`days`/`date`), matching category emoji's precedent from Step 3. Tier 3's `ItemCard` tests were rewritten to match: they now assert the callbacks fire immediately on `onChange`/click (no Done button to drive), plus two new tests asserting the recurring/one-time UI renders correctly from `item` props directly.
   - **Verified live, re-running the three historical bugs this step is designed to eliminate:** (a) cursor-jump — fast-typed a 19-character title letter-by-letter, sampled `selectionStart` after every keystroke, confirmed it always matched the typed length (never reset). (b) unmount-mid-edit loss (the PR #15 bug) — edited an item's notes, then exited edit mode ~50ms later, well before the 600ms debounce — the edit still persisted, because the pending debounce lives in the hook (which never unmounts), not in the `ItemCard` component that disappears when edit mode ends. This is a structural fix, not a patch: the bug class can't recur since there's no per-component draft left to lose. (c) flash-revert (the PR #16 bug) — structurally impossible now too, since nothing ever resets a field to a stale snapshot; inputs read `item` directly, always.
5. **Undo-for-deletes** — fully independent, smallest and most isolated, natural last step regardless of order. **Done (2026-08-28) — this closes out the redesign.** Deletes stay immediate (no confirmation dialog, same as everywhere else), but `App.tsx` now captures a snapshot of the category/item *and its original array index* right before deleting, shows a bottom-of-screen `UndoToast` ("Category deleted" / "Item deleted" + an Undo button) for 6 seconds, and re-inserts the snapshot at that index via new `restoreCategory`/`restoreItem` hook functions if Undo is tapped. A second delete while one toast is already showing replaces it rather than stacking — there's only ever one `pendingUndo` slot. New `App.test.tsx` (first test file for `App.tsx`) covers the full flow end-to-end: delete → toast → Undo → restored, for both categories and items, plus auto-dismiss-after-timeout and the replace-not-stack behavior. Verified live against a throwaway Firestore document for both categories and items: toast appears, Undo restores it, and the restored item/category persists after a hard reload. (Diagnostic note: initial live-testing runs appeared to show the toast never rendering at all, despite passing unit tests — root cause was purely a testing-methodology artifact, not a bug: each multi-step manual setup in the browser tool took longer in real wall-clock time than the 6-second auto-dismiss window, so the toast had already dismissed by the time each check ran. Confirmed by clicking and checking within a single script with a short in-script delay instead of separate round-trips.)

**Full end-to-end UAT on a real device (2026-08-26), after Step 4 landed:** every autosave path confirmed working — child's name, category name, item title/notes/time, sub-step text (all show Saving→Saved live); toggling done/undone, the one-time/recurring switch, the day picker, emoji, and add/delete all still save immediately as expected; no Done button anywhere; fast typing never jumps the cursor; editing a field and immediately exiting edit mode before the debounce fires still saves correctly (the exact PR #15/#16 bug class, confirmed gone). The only gap found (adding a *new* sub-step doesn't autosave while typing) is expected by design and already captured above as a parked follow-up.

**Real-device regression found *after* that UAT, same day, on mobile — "typing sync issue" back — root-caused and fixed:** `useSchedule.ts`'s `onSnapshot` listener has always unconditionally overwritten local `data` with whatever Firestore just pushed. Before Steps 2-4, the per-item draft shielded displayed text from this (inputs read the draft, not `data`), so it never mattered. Removing that draft reopened the race: if a snapshot arrives (another device's edit, the periodic reset check, or even this device's own earlier write echoing back) while a debounce is still pending for a *different* field, the incoming snapshot still has the old value for the field being typed, and overwrites it mid-edit. Mobile's higher latency widens the window, making it far more noticeable there. **Fixed:** the `onSnapshot` callback now skips applying an incoming snapshot while `pendingCountRef.current > 0` (this device has any unconfirmed local edit, debounced or in-flight) — reusing the exact same signal `saveStatus` already relies on. Once everything settles, the next snapshot (reflecting this device's own now-confirmed writes) applies normally. Verified two ways: a unit test that fails without the fix (reverted it to confirm, then restored), and live with two real browser tabs — Tab A typing a title, Tab B toggling an unrelated item mid-keystroke — Tab A's in-progress text survived, and still saved correctly once the debounce settled (confirmed after a hard reload).

**Sequencing note (revised 2026-08-25, resolved 2026-08-26):** the automated test suite (all 3 tiers) shipped ahead of this redesign as planned — see [Automated testing scope](#automated-testing-scope). Tier 1 and Tier 2's original tests needed no changes at all through every step. Tier 3's `CategorySection` tests were unaffected throughout. Tier 3's `ItemCard` tests *did* need their trigger step rewritten once Step 4 removed the Done button, exactly as anticipated here — done as part of Step 4 above.

## Field edit revert (shipped)

Scoped 2026-09-02. Raised by a parent: "if you start editing the wrong thing," there's currently no way to get the old value back — autosave-as-you-type (the editing UX redesign, above) means the previous text is gone as soon as you've typed over it, unlike the already-shipped [undo-for-deletes](#editing-ux-redesign-ready-to-pick-up-later).

**Why this is a different problem from undo-for-deletes:** a delete is a single, discrete, destructive action with one obvious moment to hang a toast on. A text edit isn't discrete — it's a stream of keystrokes with no natural "this edit is done" boundary now that the per-item Done button is gone. Reusing the delete-undo toast as-is (pop a toast every time a debounced write settles) would fire constantly during normal typing and be more annoying than helpful.

**Chosen direction:** a per-field revert, not a toast. The first time a field changes during an edit-mode session, capture its value at that moment (before the change). While the field's live value differs from that captured snapshot, show a small revert control (e.g. a ⟲ icon) next to it; tapping it writes the snapshot's value back through the exact same debounced-write path as a normal edit — no special "undo" write path, just typing the old value back in, so it stays consistent with everything else being "just editing." One-shot per field (reverts to where you started this session, not a multi-step undo stack) — matches the actual complaint ("I lost what was there") without the complexity of full undo/redo history.

**Which fields:** the text fields that autosave per-keystroke — child's name, category name, item title/notes/time, sub-step text. Single-tap controls (emoji, day picker, one-time/recurring toggle, date) are out of scope — a wrong tap there is trivially re-tapped back, no lost typing to recover.

**Snapshot lifetime (needs to be forgiving, not just "while still focused"):** the scenario that prompted this is someone editing the wrong field and *not* noticing until after they've moved on — so the revert option can't disappear the moment the field blurs. Current thinking: keep each field's snapshot alive for the rest of the edit-mode session (cleared when edit mode is exited, or once that field's revert is used). Simpler than time-boxing it like the delete-undo's 6-second toast, and matches "I want the safety net until I explicitly leave editing," but means a stale snapshot could sit around for a while during a long edit session — worth watching for during UAT.

**Explicitly out of scope for v1:** multi-step undo (Ctrl+Z-style history through every keystroke), non-text fields, and anything surviving a page reload or exiting edit mode — this is local, ephemeral UI state, not persisted, and doesn't need to sync across devices.

**Built (2026-09-03), not yet merged.** New `useEditRevert(editMode)` hook (`src/hooks/useEditRevert.ts`) holds snapshots in a ref (not state, so capturing one doesn't force a render on every keystroke) keyed the same way `useSchedule.ts` already keys its debounced writes (`childName`, `category:<id>:name`, `item:<id>:title`, etc.) — no relation between the two Maps, just a consistent naming convention. Three functions: `capture(key, currentValue)` (records the value once, first call only, per key, per edit-mode session), `isDirty(key, currentValue)` (has a snapshot, and the live value has actually diverged from it), and `revert(key)` (returns the snapshot and clears it — one-shot, not a stack). A `useEffect` clears every snapshot when `editMode` flips to `false`. A small `RevertButton` component (`src/components/RevertButton.tsx`, a "⟲" icon) renders next to a field whenever `isDirty` is true; it stops the click from bubbling to any ancestor's own `onClick` (several of these fields sit inside a larger clickable row, like an item's expand/collapse toggle). Wired into every target field: child's name (`App.tsx`), category name (`CategorySection.tsx`), and item title/notes plus sub-step text (`ItemCard.tsx`) — each `onChange` calls `revert.capture(key, <value before this change>)` before applying the edit, and each field's revert button calls `revert.revert(key)` and feeds the result back through the exact same setter used for a normal edit. (Item *time* was one of the original six fields wired here — removed 2026-09-04, see below.)
- New `useEditRevert.test.ts` (5 tests): not dirty until captured-and-changed, a second edit doesn't overwrite the first snapshot, revert is one-shot (a second revert call returns nothing), independent snapshots per key, and everything clears when edit mode exits.
- Verified live against a scratch document: edited an item's title, confirmed the revert icon appeared and restored it; repeated the edit, deliberately moved focus to an unrelated field (category name) before reverting, confirming the icon doesn't require staying focused on the field — the actual scenario that prompted this feature; edited both the child's name and a category name simultaneously, confirmed two independent revert icons; reverted one and left the other changed, then exited and re-entered edit mode, confirming the un-reverted value persisted (correct — reverts are opt-in, not automatic) while its revert icon was gone (correct — a fresh edit-mode session has no snapshot of a value from a previous session).
- **Process note:** while wiring this up, discovered `npx tsc --noEmit` (used for "typecheck clean" verification throughout this whole project) had been silently checking nothing all along — the root `tsconfig.json` only declares project references (`files: []`), which `tsc` ignores unless run in `--build` mode. The real check is `npx tsc -b` (what `npm run build` actually runs). Re-ran it here and it caught two real, previously-invisible type errors (test files missing the new required `revert` prop) — fixed both. CI (`test.yml`) also never ran a typecheck step, only `npm run test`, so a real type error could have merged undetected in any earlier PR. Worth adding a typecheck step to CI — not done as part of this feature, flagging it separately.

## Skip a recurring item for one day (shipped)

Captured 2026-09-04: a recurring item (scheduled via `days`) sometimes genuinely doesn't apply on one particular occurrence — the dog's at the groomer, no evening chore because the family's eating out. There was no honest way to reflect that: marking it done anyway is a lie, leaving it unchecked drags down today's progress count for something that was never really expected, editing `days` to drop today's weekday changes the schedule going forward (not just today) and is easy to forget to revert, and a one-time item's `date` field is for something that only ever happens once, not an exception to something recurring.

**Design, decided 2026-09-04:**
- **Data model:** new `skipped: boolean` on `ScheduleItem`, sitting next to `done` — transient, reset nightly by the same `resetCompletion()` that already clears completion state, not a persisted list of skipped dates. This is a same-day, in-the-moment call ("this doesn't apply today"), not planning a skip weeks in advance.
- **Mutual exclusivity with `done`:** the two states can't both be true for the same day — marking an item skipped clears `done` (and every sub-step's `done`), and marking it done (via the existing checkbox) clears `skipped`. Whichever action happens last wins.
- **Progress counting:** a skipped item drops out of today's active/total count entirely, in both `App.tsx`'s overall progress and `CategorySection.tsx`'s per-category progress — the same layer that already filters by `isItemScheduledOn`, just one more condition alongside it. This is the actual point of the feature, not just a display choice.
- **Visibility:** a skipped item stays in the today list — not hidden — but reads as clearly distinct from "done," not a re-skin of the same dimmed-and-struck-through treatment (that would be too easy to misread as completed at a glance). Concretely: the item-level checkbox gets a genuine third visual state alongside the existing outlined-ring (not done) and filled-white-with-checkmark (done) — a muted-filled circle with a dash instead of a checkmark — plus a small "Skipped today" label near the title.
- **Control placement:** a small icon on the item's top-level row, next to the drag handle — but in **edit mode**, not the normal Today view (reversed 2026-09-08, see below).
- **Undo:** no toast needed — tapping the same control again un-skips it, the same interaction as un-completing a done item by tapping its checkbox again. A toast makes sense for delete (data actually leaves an array); this is just flipping a flag back.
- **Who can do it — reversed 2026-09-08:** originally scoped as available in the normal view, not gated behind the edit PIN, reasoning that it's "the same trust level as the done-checkbox itself." **User pushback, same day:** skip is a subtler tool for a kid to lean on than the done checkbox — marking something done when it isn't is a fairly direct lie, while framing something as "doesn't apply today" is an easier story to tell yourself, and it quietly removes the item from the count without looking like anything was touched. It also fits the app's existing philosophy better: edit mode is PIN-gated specifically so *structural* decisions (what's scheduled, what counts) stay with a parent, and skip is exactly that kind of decision, not a "did I do it" tap. **Moved behind the edit PIN, same day.** A kid still *sees* a skipped item's distinct state in the normal view — they just can't set or clear it themselves.

**Explicitly out of scope for v1:** planning a skip for a future date in advance, skipping an individual sub-step rather than the whole item, and any change to `isItemScheduledOn`'s actual day-of-week/date matching — skip is a same-day override layered on top of that, not a change to the matching logic itself.

**Built (2026-09-08), not yet merged.** New `skipped: boolean` on `ScheduleItem` (`types.ts`), backfilled to `false` by `normalize()` for old documents and reset to `false` by `resetCompletion()` alongside `done`, same as every other migration/reset field. New `toggleSkip(categoryId, itemId)` in `useSchedule.ts` flips the flag — turning it on also clears `done` and every sub-step's `done`; turning it off just clears the flag, since there's nothing meaningful to restore back to. `toggleItem` and `toggleSubStep` both unconditionally clear `skipped` too, so the mutual-exclusion invariant holds regardless of which direction a change comes from, not just the one path that was expected to matter.
- **Progress counting:** `CategorySection.tsx` now computes `scheduledToday` (everything matching `isItemScheduledOn`, used for what actually *renders* in view mode) separately from `countedItems` (`scheduledToday` minus anything skipped, used for the category's own `total`/`doneCount`/`allDone`) — the split matters because a skipped item still needs to show up in the list, just not count. `App.tsx`'s overall progress got the same `&& !it.skipped` condition added to its existing scheduling filter.
- **UI (`ItemCard.tsx`):** the item-level checkbox has a third state in *both* modes — the existing outlined ring (not done) and filled-white-with-checkmark (done) in view mode, plus a new muted fill with a dash glyph for skipped (`bg-white/25` in view mode; `bg-black/10 dark:bg-white/10` in edit mode, matching that mode's neutral palette instead of the bold per-category color). A "Skipped today" label replaces the sub-step count line in view mode when skipped, and the title dims (`opacity-70`) without the strikethrough `done` gets, so the two states don't read the same at a glance; edit mode gets a matching inline "skipped today" label next to the title inputs. The "⊘" toggle button itself sits on the row next to the drag handle, **edit mode only** — matches the app's existing convention of plain Unicode glyphs for UI chrome rather than an icon library.
- Covered by 2 new hook tests (skip clears done/sub-steps and is reversible; marking done clears skip) and 5 new component tests (the icon calls `toggleSkip` in edit mode; the edit-mode dash checkbox and label render when skipped; the toggle never renders in view mode, skipped or not; the read-only view-mode state looks distinct from done, with the label and no strikethrough; the main checkbox still works normally on a skipped item) plus 2 new `storage.test.ts` cases (`normalize` backfill, `resetCompletion` clearing an existing skip).
- Verified live against a scratch document, both before and after moving the control: skipping an item immediately dropped both the category's and the overall progress count by one; the item stayed visible with the dash checkbox and label in whichever mode wasn't doing the toggling; tapping the icon again reversed everything exactly; after moving the control, confirmed the icon appears in edit mode (with the matching dash checkbox and label there too) and is completely absent from the normal Today view, skipped or not.

## History — look back at past days (scoped, not yet built)

Captured 2026-09-02: completion state (`item.done` / `subStep.done`) lives directly on the one live Firestore document and gets wiped every night by `resetCompletion()` (see `lib/storage.ts`) — once that runs, yesterday's done/not-done state is gone for good. This isn't just a missing UI; there's no data to show one yet.

**Design, decided 2026-09-04:**
- **Storage:** a new, separate Firestore collection (one small document per date, e.g. `history/2026-09-04`) — not embedded in the main `household/schedule` document. Keeps every device's always-on real-time listener fast (it never downloads years of history), and a history read only costs anything when someone actually opens it.
- **Snapshot content:** a full, self-contained copy of that day — category names/emoji/color, item titles/emoji, and done-state (including sub-steps) for whatever was actually scheduled that day. Not just item/sub-step IDs referencing the live schedule, since those go stale as items get renamed or deleted over time (which will keep happening as the chore list evolves) — a self-contained snapshot stays meaningful indefinitely, independent of later edits to the live schedule.
- **Write timing:** captured inside the existing `resetIfStale()` transaction in `useSchedule.ts`, right before `resetCompletion()` wipes completion state for the day that's ending. That transaction already guards against duplicate runs (only the first device to check after midnight finds a stale `lastResetDate` and actually executes; every other device's check that same day is a no-op) — the history write rides along inside it for free, no new cross-device coordination needed.
- **Retention:** none — no expiration or cleanup policy. Even years of small daily documents is negligible for Firestore; capping this now would be solving a problem that doesn't exist.
- **UI:** extend `WeekView`'s existing day-picker rather than build a separate view/tab. Add previous/next week navigation to the day strip (today it only reaches `currentWeekDateKeys()`, the current week); selecting a day in the past switches that day's list from the current live-schedule preview to its persisted snapshot, rendered with real checkmarks (the bold, view-mode style, matching Today) instead of the plain informational pills past/future days show today. Selecting today or a future day keeps the current live-preview behavior unchanged.
- **Editability:** read-only. History shows exactly what happened and can't be changed after the fact — simplest to build, and avoids reopening edit/sync/undo complexity for what would be a rare correction.
- **Fetching:** a lightweight one-off read (`getDoc`, not `onSnapshot`) whenever a past date is selected — a history snapshot is immutable once written, so it doesn't need the always-listening real-time sync the live schedule uses.

**Explicitly out of scope for v1:** editing a past record, any retention/cleanup policy, and showing history for a date before this feature shipped — there's no snapshot for days that predate it, so those will just show nothing, not an error.

**Not yet started** — no branch, no implementation.

## What's next — a single-task focus view (shipped 2026-09-09)

Captured 2026-09-08: a long checklist can overwhelm a kid in a way it doesn't overwhelm a parent. This spotlights one task at a time instead of the full category grid — matches the app's own name.

**Design, decided 2026-09-08:**
- **Sequencing:** derived entirely from the order that already exists and is already editable — category order, then item order within each category (the same order edit mode's drag-and-drop reordering already controls). No new priority field or pinning concept; a parent influences the flow exactly by reordering things the way they already can today. This is also why categories-themselves reordering (item 1 under Next steps, not yet built) becomes more directly useful once this ships — it'd shape the whole day's flow, not just one category's item order. **Superseded 2026-09-09:** category/item order alone couldn't interleave one specific item from each category without moving whole category blocks — see [Reorder focus order](#reorder-focus-order-shipped-2026-09-09) below, which adds an explicit, independent focus order on top of this as a fallback.
- **Scope of the flow:** one continuous sequence across every category, not one category at a time — finish Morning Routine, flow straight into Chores, then Soccer Prep, so the kid never has to think about which category they're in, just what's in front of them right now.
- **What "next" means:** the first not-done item in that sequence that's actually scheduled for today (the same `isItemScheduledOn` filter Today already uses) and not [skipped](#skip-a-recurring-item-for-one-day-shipped). No "position" is ever stored — leaving focus mode and coming back always re-derives from current completion state, so there's nothing that can get out of sync.
- **Completing an item:** the focus card's checkbox is the same `toggleItem` already used everywhere else — for an item with sub-steps, tapping it completes all of them together, exactly like today's behavior. Nothing focus-mode-specific needed there.
- **Entry/exit:** a toggle on the existing Today view (a button, likely next to Edit) swaps the category grid for the single-card flow; a "See full list" link swaps back. Not a third persistent tab like Week — this is a different way of looking at today's items, not a different dataset.
- **Finishing:** once every item for the day is done, the flow ends on a completion screen (reusing the existing "🎉 Everything done — great focus today!" message) with a way back to the full list.
- **Availability:** view mode only, same as everything else meant for day-to-day use rather than structural editing — no focus toggle while in edit mode.

**Explicitly out of scope for v1:** any session-only reordering within the flow (e.g. a "later" action that lets you skip past one item and come back to it before finishing) — real added complexity for a nice-to-have; v1 goes straight through in sequence order. Also out of scope: any new field for prioritizing items independent of their edit-mode order.

**Built (2026-09-09), shipped.** New `FocusView`/`FocusComplete` components (`src/components/FocusView.tsx`) and a `focusMode` boolean in `App.tsx`. The "next" item is recomputed on every render — no position stored for *which item is currently focused* — by walking the sequence from `buildFocusSequence` (originally plain category/item order; now factors in the explicit focus order too, see [Reorder focus order](#reorder-focus-order-shipped-2026-09-09) below) and returning the first item where `isItemScheduledOn` is true, `skipped` is false, and `isItemDone` is false; the same `toggleItem`/`toggleSubStep` used everywhere else drive the card's checkbox and sub-step list, so completing an item (all sub-steps together, exactly like today's behavior) just causes the next render to pick a different "next" item — nothing focus-mode-specific to keep in sync. A 🎯 Focus / 📋 Full list toggle sits next to Edit on the Today view (hidden when nothing's scheduled today, matching the progress card's own gating); a "See full list" link inside the focus card does the same thing. A `useEffect` clears `focusMode` whenever `editMode` turns on, so entering edit mode (PIN or not) always drops back to the full list — focus mode has no edit-mode variant. Once nothing is left to focus on, `FocusComplete` reuses the exact "🎉 Everything done — great focus today!" message from the progress card.
- Covered by 5 new `App.test.tsx` tests: shows the correct first item and advances past it once complete; doesn't advance when only one of several sub-steps is done; "See full list" returns to the grid; entering edit mode exits focus mode; the completion screen appears once every scheduled item is done.
- Verified live against the real household document (no separate test environment exists for this app): Focus correctly landed on "Pack School Bag" (the first not-done item in Morning Routine's order), toggling one of its sub-steps didn't advance the flow, completing the item advanced focus straight into "After School" in Chores (crossing the category boundary correctly), and clicking Edit while in focus mode dropped back to the full list and prompted for the parent PIN as normal. Checked at a 375px mobile width too. Every state change made during verification was reverted immediately afterward, leaving the real document exactly as found (8/21 done, Pack School Bag not done).

## Reorder focus order (shipped 2026-09-09)

Raised by the user immediately after trying the merged "What's next" view and [category-level reordering](#next-steps): a parent wanting one specific Soccer Prep item to come before one specific Morning Routine item had no way to say so — category drag only moves a whole category as a block, and item drag only reorders within one category. True interleaving needed an order independent of category/item structure.

**Design, decided 2026-09-09 (via direct back-and-forth with the user):**
- **A dedicated flat reorder screen**, not dragging items across category boundaries in the existing grid — chosen over the alternative (letting a parent drag an item out of its category card into another one) because that would blur "category" as a grouping/scheduling concept and change what category an item belongs to, a bigger behavior change than just wanting a different focus flow.
- **Used only by focus view.** The user was explicit: this order does not replace or affect category/item order anywhere else — the main Today grid and edit mode's per-category item lists are untouched. It's a second, independent order that only `buildFocusSequence` reads.
- **Explicit list wins, falls back per-item.** Once set, focus order is `data.focusOrder` (a flat array of item ids) first, then any item not in that list — a brand-new item, or every item before this was ever touched — appended afterward in the existing category/item order. No all-or-nothing switch to flip.

**Built (2026-09-09), shipped.** New `focusOrder: string[]` field on `ScheduleData` (`types.ts`), backfilled to `[]` by `normalize()` for old documents. New pure `buildFocusSequence(data)` in `src/lib/focusOrder.ts` — replaces the plain category/item walk `App.tsx` used for "What's next": maps `focusOrder` ids to their `{category, item}` pairs (dropping any id for a since-deleted item), then appends every item not in that list, in ordinary category/item order. New `reorderFocusOrder(orderedIds)` in `useSchedule.ts` sets `focusOrder` directly and immediately (not debounced).
- **UI:** a "Reorder focus flow" button in the header, next to "Done editing" (edit mode only), opens `FocusOrderEditor`, a full-screen overlay (not a small modal like `PinPrompt` — this list can be long) showing items in one flat `@dnd-kit` sortable list (`SortableFocusRow`: emoji, title, and a small category-emoji-plus-name caption per row, drag handle only — no checkboxes or editing here, this screen only sets order). "Done" closes it back to the edit-mode grid underneath, which is untouched.
- Covered by 8 `lib/focusOrder.test.ts` tests (falls back to category/item order when empty, interleaves across categories when set, appends missing items, drops ids for deleted items, carries the right category per item, plus 3 for `mergeVisibleReorder` below), 1 `useSchedule.test.ts` test (`reorderFocusOrder` sets and persists immediately), 5 `FocusOrderEditor.test.tsx` tests (lists every item with its category, honors an existing `focusOrder` over plain category order, "Done" calls back, only shows today's items, shows a distinct "Nothing scheduled today" message when the schedule has items but none run today), and 1 `App.test.tsx` test (the button opens the editor from edit mode, "Done" returns to the grid).
- Verified live against a scratch document with real dispatched pointer events (same `isPrimary: true` technique as the category-drag verification): dragged "Pack Soccer Bag" from last to first in the flat list, closed the editor, confirmed the main Today grid still showed categories in their original Morning Routine → Chores → Soccer Prep order (untouched), then opened Focus and confirmed it started on "Pack Soccer Bag" instead of "Make Your Bed" — the exact cross-category interleaving that prompted this feature.

**Refined 2026-09-09, same day, after the user tried it live:**
- **Only shows today's scheduled items.** The initial version listed every item in the whole schedule, including ones that only ever run on other weekdays — clutter for a screen that's explicitly about today's flow. `FocusOrderEditor` now filters to `isItemScheduledOn` before rendering. The tricky part: `focusOrder` itself still has to cover every item regardless of day (an item's day-eligibility changes what's *visible* here, not what's *in* the order), so saving a drag can't just write the filtered subset as the new whole order — that would silently drop every other-day item from `focusOrder` the next time it's edited. New pure `mergeVisibleReorder(fullSequence, visibleIds, reorderedVisibleIds)` in `lib/focusOrder.ts` splices the freshly-dragged visible subset back into the full sequence, leaving every hidden (other-day) item exactly where it already was. Verified live: temporarily excluded "Make Your Bed" from today via its day picker, confirmed it disappeared from the reorder screen but stayed in the edit-mode grid; dragged "Feed the Dog" to the front of the (now Make-Your-Bed-less) list; re-enabled "Make Your Bed" for today and confirmed it reappeared in its original position — first, ahead of "Feed the Dog" — rather than being lost or shoved to the end.
- **Button moved.** "Reorder focus flow" was originally down in edit mode's bottom settings section (next to Parent PIN/Reset), easy to miss. Moved up into the header's button row, next to "Done editing" — visible immediately upon entering edit mode, no scrolling required.

6. **Flexible recurrence (beyond weekly)** — just captured 2026-08-28, not yet scoped.
